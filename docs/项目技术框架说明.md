# Jens 扫描软件自动化测试平台技术框架说明

## 1. 项目定位
**基于 Python + Airtest + PyQt5 的 Windows 桌面 UI 自动化平台，采用 Step 资产化、Case/Task 编排化、Runner 统一执行、Artifacts 归档化 的架构模式，面向 CrealityScan 软件构建可复用、可维护、可追溯的自动化测试体系。**


项目当前已经形成一条完整闭环：

1. 用历史 `.air` 用例沉淀步骤能力
2. 用 `Qt` 平台选择步骤、配置参数、保存用例/任务
3. 用统一 Runner 执行 Case
4. 在运行结束后归档截图、日志、结构化结果和 HTML 报告

这套设计的本质是把“录制脚本”升级为“步骤库 + 编排平台 + 执行引擎”三层结构，目标是提升复用性、维护性和结果可追溯性。

## 2. 技术栈

### 2.1 语言与运行环境

- Python
- Windows 桌面环境
- PyInstaller 安装态兼容

### 2.2 核心依赖

- Airtest
  - 用于 UI 自动化执行、模板匹配、设备连接、截图采集
- PyQt5
  - 用于步骤编排平台、任务管理、运行控制与结果展示

### 2.3 运行对象

- 被测应用：`CrealityScan`
- 默认设备连接：`Windows:///`
- 默认窗口标题关键字：`CrealityScan`

## 4. 目录职责说明

### 4.1 根目录关键文件

- `platform_app.py`
  - 桌面平台总入口，同时支持 `--run-case` 子命令
- `jens_runner_entry.py`
  - Runner 主实现，负责一次 Case 的完整执行
- `jens_runner_helper.py`
  - 安装态辅助入口，优先从命令行或环境变量读取 Case 路径
- `jens_runtime.py`
  - 屏蔽源码运行与 PyInstaller 安装运行的路径差异
- `requirements.txt`
  - 执行引擎依赖，仅包含 `airtest`
- `requirements-ui.txt`
  - 平台 UI 依赖，仅包含 `PyQt5`

### 4.2 业务目录

- `engine/`
  - 核心执行逻辑
- `jens_platform/`
  - 桌面编排平台
- `steps/`
  - 步骤库
- `cases/`
  - 用例 JSON
- `tasks/`
  - 任务 JSON 与任务辅助脚本
- `config/`
  - 通知配置等运行配置
- `docs/`
  - 项目文档
- `用例仓库/`
  - 原始 `.air` 用例素材库，当前安装包不包含

## 5. 核心数据模型

### 5.1 Step 模型

一个 Step 由三部分构成：

1. 元数据：`step.json`
2. 实现代码：`impl.py`
3. 资源文件：`templates/*.png`、可选 `presets.json`

目录约定示例：

```text
steps/crealityscan/import_project/v1_0_0/
├─ impl.py
├─ step.json
└─ templates/
```

Step 的加载规则由 `engine/executor.py` 固定：

- `step_id=crealityscan.import_project`
- `version=1.0.0`
- 映射到模块：
  - `steps.crealityscan.import_project.v1_0_0.impl:run`

这意味着步骤发现与步骤执行是解耦的：

- 平台扫描 `step.json`
- 引擎按 `step_id + version` 动态 import `run(ctx, params)`

### 5.2 Case 模型

Case 是一次自动化流程编排，关键字段如下：

```json
{
  "case_id": "example_case",
  "name": "示例用例",
  "app": {
    "window_title_contains": "CrealityScan",
    "device_uri": "Windows:///",
    "log_dir": "C:\\Users\\...\\Logs"
  },
  "keywords": ["Traceback", "Exception", "ERROR", "失败", "崩溃"],
  "steps": [
    {
      "id": "common.activate_window",
      "version": "1.0.0",
      "name": "激活/置顶 CrealityScan",
      "params": {},
      "on_fail": { "action": "abort" }
    }
  ]
}
```

Case 的职责是定义：

- 运行对象是谁
- 需要扫描哪些日志关键词
- 步骤按什么顺序执行
- 每一步失败时如何处理

### 5.3 Task 模型

Task 本质上仍然是 Case JSON，只是默认存放在 `tasks/`，用于主界面任务队列的批量运行。

它解决的是“多 Case 串行执行”的问题，而不是新增一套复杂协议。

## 6. 关键执行链路

### 6.1 UI 启动链路

入口是 `platform_app.py`：

- 普通启动时加载 PyQt5，修正 Qt 插件路径
- 然后进入 `jens_platform.main.main()`
- 创建 `MainWindow(project_root)`
- 扫描步骤库，加载任务队列，展示界面

### 6.2 Runner 启动链路

存在两种触发方式：

1. UI 运行任务
2. 命令行或安装程序直接传入 `--run-case`

最终都会进入：

- `jens_runner_entry.run_case(case_path)`

该函数完成以下动作：

1. 解析应用根目录和资源根目录
2. 加载 Case JSON
3. 创建 `artifacts/<case_name>_<timestamp>/`
4. 对 Airtest 日志命名做补丁
5. 调用 `auto_setup()` 初始化 Airtest
6. 连接设备 `connect_device(device_uri)`
7. 调用 `execute_case(case, run_dir)`
8. 解析设备信息和日志关键词
9. 写入 `result.json`
10. 生成 `report.html`
11. 生成 `summary.json`
12. 成功则清理轻量临时产物，失败则复制 CrealityScan 日志

### 6.3 Step 执行链路

`engine/executor.py` 的 `execute_case()` 是真正的逐步执行器。

每个 Step 的流程为：

1. 校验 Step 数据结构
2. 提取 `step_id/version/name/params/on_fail`
3. 执行前尝试激活窗口
4. 通过 `resolve_step_callable()` 动态加载步骤实现
5. 注入当前步骤环境变量
6. 调用 `run(ctx, params)`
7. 成功则记录 passed
8. 失败则：
   - 抓失败截图
   - 根据 `on_fail` 决定 `retry / continue / abort`
9. 清理当前步骤环境变量

`on_fail` 支持三类策略：

- `abort`
  - 当前步骤失败后立即终止整个 Case
- `continue`
  - 当前步骤失败但不中断后续步骤
- `retry`
  - 失败后按指定重试次数与等待时间重试

这部分设计使得执行策略不是硬编码在步骤实现里，而是外置在 Case 编排层。

## 7. 平台层设计

### 7.1 步骤发现机制

`jens_platform/step_registry.py` 通过扫描 `steps/**/step.json` 发现所有步骤，并做稳定排序。

特点：

- 同时兼容源码态与安装态资源目录
- 以 `step.json` 为唯一发现依据
- 对元数据错误有容错，不会因单个坏文件导致全量扫描失败

### 7.2 Case 编辑与保存

`jens_platform/case_store.py` 中的 `CaseModel` 负责平台内存模型与 JSON 文件互转：

- `to_dict()`
- `from_dict()`
- `save_case_json()`
- `save_task_json()`

默认行为：

- 用例保存到 `cases/user/`
- 任务保存到 `tasks/`

### 7.3 任务队列运行

主界面运行入口 `_run_case()` 不直接执行当前编辑内容，而是按任务栏顺序串行执行多个 Task。

它的定位更接近：

- 小型调度器
- 顺序执行器
- 结果集中查看器

### 7.4 子进程运行模型

`jens_platform/runner.py` 中的 `AirtestRunResult` 使用 `QProcess` 拉起子进程。

优点：

- UI 与执行器隔离，界面不会被长时间阻塞
- 可以实时读取标准输出
- 可以解析输出中的 `run_dir` 与 `report`
- 支持 `terminate()` + 超时 `kill()` 的停止逻辑

这比在 UI 主线程内直接执行自动化脚本稳得多。

## 8. 日志、截图与报告机制

### 8.1 失败截图

在 `execute_case()` 中，步骤异常时会自动调用 `_try_snapshot()` 生成失败截图，保存到：

```text
artifacts/<run_dir>/screenshots/
```

这满足了 UI 自动化里最关键的排障诉求之一：失败现场可回溯。

### 8.2 日志分析

`engine/logs.py` 提供两类增强能力：

1. `extract_device_info()`
   - 从 CrealityScan 日志尾部提取设备名、序列号、连接类型、固件版本
2. `scan_keywords()`
   - 对日志目录做关键词扫描，提取错误线索

当前默认关键词来自 `engine/defaults.py`：

- `Traceback`
- `Exception`
- `ERROR`
- `失败`
- `崩溃`

### 8.3 HTML 报告

`engine/report_html.py` 负责渲染最终 HTML 报告。

报告输入包括：

- Case 名称
- 起止时间
- Step 结果
- 日志关键词命中
- 设备信息

因此它不是单纯的 Airtest 原始报告，而是项目级的二次汇总报告。

## 9. 步骤库现状

当前项目已扫描到 `19` 个步骤定义文件，主要分为两类：

### 9.1 通用步骤

- `common.activate_window`

用于执行前激活并置顶目标窗口，是稳定性的基础步骤。

### 9.2 CrealityScan 业务步骤

覆盖典型扫描流程：

- 导入工程
- 创建工程
- 创建扫描
- 扫描参数设置
- 点距设置
- 扫描到目标帧后停止
- 后处理、融合、贴图、打包等动作

其中部分步骤还带有 `presets.json`，例如：

- `configure_scan_params`
- `configure_scan_params_ferret`
- `configure_scan_params_raptor`
- `configure_scan_params_s1`

这说明当前平台已经从“固定脚本”演化到了“参数化步骤”阶段。

## 10. 从 Airtest 脚本到 Step 的迁移机制

`jens_platform/air_step_importer.py` 提供旧 `.air` 用例迁移能力。

它的核心流程是：

1. 读取 `.air` 目录
2. 解析其中的 `.py`
3. 提取支持的动作
4. 生成新 Step 目录
5. 写入 `step.json`
6. 写入 `impl.py`
7. 复制模板图片到 `templates/`

当前明确支持的迁移动作以 Airtest 常见指令为主：

- `touch`
- `wait`
- `swipe`
- `sleep`
- `Template`

这条能力非常关键，因为它决定了旧资产不会被推倒重来，而是可以转化为步骤库资产。

## 11. 运行态与安装态兼容设计

`jens_runtime.py` 把路径访问分成两类：

- `get_app_root()`
- `get_resource_root()`

这解决了源码运行与 PyInstaller 安装后的资源位置差异：

- 源码态：资源就在项目目录
- 安装态：资源可能在 `_MEIPASS` 或 `_internal`

这类封装是必要的，否则：

- 步骤扫描会失效
- 模板路径会失效
- Case/Task/Docs/Artifacts 的读写会混乱

## 12. 当前架构优点

### 12.1 解耦清晰

- 平台只关心编排和运行控制
- 引擎只关心执行
- Step 只关心单步动作

### 12.2 易于扩展

新增 Step 不需要修改执行引擎，只要遵守目录与接口约定即可。

### 12.3 易于复用

同一 Step 可被多个 Case/Task 复用，避免复制粘贴脚本。

### 12.4 可追溯性较强

运行结果同时有：

- 结构化 JSON
- HTML 报告
- 失败截图
- 原始日志
