# Mac 操控滑轨：可行性评估与落地方案

> 结论先行：**方案可行，且与现有架构天然契合，推荐直接走通。**
> Mac 通过局域网 IP 连到 Windows 上的 `motion_service`，由 Windows 侧（32 位 Python + zauxdll.dll）驱动 ECI1308 滑轨控制器。
> 你想要的"setp（单步脉冲）"控制，在现有协议里就是 `move_relative(±pulse)`，Mac 端可做到与 Windows 控制台完全一致。

---

## 1. 现有架构（代码依据）

```
[Mac 端纯 Python 客户端] ──TCP:5000──► [Windows 32位Python]
  motion_client.py（跨平台，仅标准库）      motion_service.py（Socket 服务端）
                                                  │
                                          zmotion_controller.py（ctypes 封装）
                                                  │
                                          zauxdll.dll（正运动 ZMotion SDK，仅 Windows DLL）
                                                  │
                                          ECI1308 控制器（网口，192.168.0.11）
```

关键事实（已在代码中核实）：

| 组件 | 文件 | 关键点 |
| --- | --- | --- |
| 硬件/驱动层 | `zmotion_controller.py` | `ctypes.CDLL` 加载 `zauxdll.dll`，**仅 Windows、且必须 32 位 Python**，不可能直接跑在 Mac |
| 服务端 | `motion_service.py` | `HOST='127.0.0.1'`，`PORT=5000`，每客户端一个线程，命令用换行分隔 JSON 传输 |
| 客户端 | `motion_client.py` | **纯标准库**（socket/json/time/threading），`create_motion_client(host, port)` 已支持任意 host/port，天然跨平台，可跑在 Mac |
| 单步脉冲（setp） | `slide_rail_ui.py` + `motion_client.move_relative` | Windows 控制台"单步脉冲"左右按钮 → `move_relative(±pulse)` → 服务端 `horizontal_move` → `move_relative(0, pulse)`（含软限位保护 + 等待到位） |
| 平台集成 | `engine/slide_rail_scan_motion.py`、`steps/slide_rail/switch_position/...` | Windows 平台已用 `motion_client` 远程调服务；**现有滑轨服务本身就是"本地通过 socket 控制硬件"，只是默认只监听了回环地址** |

也就是说：**滑轨控制天然已经是"客户端/服务端分离"，你的方案只是把客户端从 Windows 本机换到 Mac 上，架构上零改动，只剩几个落地细节。**

---

## 2. 可行性评估

### 2.1 结论

- ✅ **核心链路可行**：`motion_client.py` 是纯 Python、纯 socket，Mac 上可直接运行，连 Windows 的局域网 IP:5000 即可。
- ✅ **"setp 单步脉冲"零成本获得**：Mac 端调 `client.move_relative(pulse)` 即与 Windows 控制台完全相同的移动控制（同一协议、同一软限位、同一到位等待）。
- ⚠️ **前提是服务端要能对外监听**（当前只监听 127.0.0.1），详见第 3 节改动点。
- ⚠️ **前提是网络/防火墙可达**（同局域网、Windows 防火墙放行 5000）。
- ⚠️ **并发与安全**需注意（见第 4 节）。

### 2.2 为什么硬件不能搬到 Mac

`zauxdll.dll` 是 Windows PE 格式的动态库，Mac（无论 x86_64 还是 ARM）都无法加载，`ctypes.CDLL` 只在 Windows 有效，且 ECI1308 需要 32 位环境。所以"让 Mac 直接驱动硬件"这条路成本极高（需要逆向 ZMotion 的网口协议并在 Mac 侧重写驱动封装与全部软限位/安全逻辑），**当前完全不值得**。你的"Mac 发命令 → Windows 服务控硬件"正是最省成本的正解。

## 3. 落地需要的改动点（很小）

### 3.1 服务端：监听改为对外网卡

`motion_service.py` 第 17 行：

```python
# 改前
HOST = '127.0.0.1'
# 改后（监听所有网卡，或填 Windows 本机局域网 IP）
HOST = '0.0.0.0'
```

> 建议：直接用 `0.0.0.0`，或用环境变量/配置覆盖，避免每次都改代码。

### 3.2 Windows 防火墙

放行 TCP 5000 端口（专用网络配置文件）：
```powershell
netsh advfirewall firewall add rule name="motion_service" dir=in action=allow protocol=TCP localport=5000
```

### 3.3 网络连通性验证

Mac 上 `nc -vz <Windows局域网IP> 5000` 能通即可。

### 3.4 Mac 端：复用 motion_client.py（纯 Python，零依赖）

把 `motion_client.py` 拷到 Mac 侧（或作为公共库），即可：

```python
from motion_client import create_motion_client

client = create_motion_client(use_mock=False, host="192.168.x.x", port=5000)
client.connect()
client.connect_controller()          # 连控制器（如服务未自动连）
client.move_relative(10000)          # 这就是"setp 单步脉冲"：右移 10000 脉冲
client.move_relative(-10000)         # 左移
client.get_position()
client.disconnect()
```

### 3.5 Mac 平台（mac_pyautogui_poc）接入

按现有 step 机制新增一个 step，例如 `crealityscan.slide_rail_step`：

- 新增 `output/mac_pyautogui_poc/steps/slide_rail.py`，`run(ctx, params)` 里解析 `host/port/pulse`，调用 `move_relative`；
- 在 `output/mac_pyautogui_poc/registry.py` 的 `STEP_REGISTRY` 注册。

这样 Mac 的自动化用例里就能以 step 方式"单步移动滑轨"，与 Windows 平台体验一致。

## 4. 关键风险与注意事项（务必处理）

1. **并发/线程安全**：`motion_service` 里所有客户端线程共享同一个 `self.controller`（ctypes 调用、同一句柄），当前没有全局锁。
   - 单 Mac 客户端、且 Windows 控制台不并发操作时：没问题。
   - 若 Windows 控制台与 Mac 可能同时操作：建议在服务端加一把全局命令锁，串行化所有硬件命令，防止两个连接互相打断（尤其连续运动类命令）。
2. **连续运动命令的"停止"要走第二个连接**：`continuous_scan_cycle` 会在该连接的处理线程里阻塞很久，`MotionClient.send_command` 会一直等响应；所以要停止时必须像 `engine/slide_rail_scan_motion.py` 那样**新建一个客户端连接**发 `stop_continuous`。Mac 侧也要沿用这个约定。
3. **安全**：服务暴露到局域网后，任何能连到 5000 的机器都能驱动滑轨（有物理风险）。至少做到：
   - 只放行到特定 VLAN / 仅本机+Mac；
   - 更稳妥：在协议里加一个简单 token（服务端校验），或第 5 节方案 B 的 HTTP 网关里加鉴权。
4. **超时**：客户端默认 180s 超时，覆盖常规移动；长任务（下降到底约 48s+）也在范围内，但连续运动类命令不要在同一连接上等响应。
5. **丢包/断线**：TCP 是流式协议，当前用换行分帧较简单。局域网内一般稳定，但建议客户端对 `connect` 和每个命令做一次重试（最多 1~2 次），失败给出明确日志。

## 5. 备选方案对比

| 方案 | 改动量 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- | --- |
| **A. 直接打通现有 Socket 协议（推荐）** | 很小（改 1 行 + 防火墙） | 零新增依赖、复用全部现有能力（软限位/到位等待/位置日志）、Mac 与 Win 行为完全一致 | 需要处理并发锁；协议非标准 | ✅ 首选，半天内可落地 |
| **B. Windows 侧加 HTTP/REST 网关** | 中（服务端加 Flask/FastAPI） | 标准协议、curl/浏览器可测、易加鉴权、易与未来 Web 平台对接、防火墙策略更清晰 | 多一个服务进程、多一层维护 | 若后续要做"局域网 Web 平台"，推荐升级到 B |
| **C. Mac 通过 SSH 远程调 Windows 命令行** | 中 | 不需要常驻服务 | 慢、脆、难处理连续运动、需配 SSH | 不推荐 |
| **D. Mac 直连 ECI1308（去掉 Windows）** | 大 | 彻底去 Windows 依赖，最"干净" | 需逆向 ZMotion 网口协议并重写软限位/安全逻辑，风险高 | 长期可选，近期不值得 |

**推荐组合**：短期走 **A** 先跑通（Mac 拥有与 Win 一致的 setp 单步控制）；如果发现并发冲突或后续要上 Web 平台，再把服务端包一层 **B**（REST 网关）作为稳定入口，两种入口可共存。

## 6. 已落地的代码改动（本仓库内）

- `滑轨/motion_service.py`：`HOST` 改为默认 `0.0.0.0`，并支持环境变量 `MOTION_SERVICE_HOST` / `MOTION_SERVICE_PORT` 覆盖。
- `output/mac_pyautogui_poc/steps/slide_rail.py`：新增 Mac 端滑轨 step（纯标准库 Socket 客户端 + `run(ctx, params)`）。含：
  - 单步脉冲：`step` / `move_relative`（`pulse` ±，`direction` left/right），与 Windows 控制台"单步脉冲"一致；
  - 位置读取与控制：`move_absolute`（支持 `preset` 或 `pulse` 作绝对位置）、`get_position`、`set_soft_zero`、`reset_to_zero`、`connect_controller`、`emergency_stop`；
  - 换位流程：`switch_position`（对齐 Windows `slide_rail.switch_position`：下降到底 → 可选回软零点 → 绝对移动 → 按 preset 可选上升）。
  - 内置 4 个位置 preset：小物体 -30000 / 中物体 -170000 / 人脸 -370000 / 大物体 -580000（换位后默认上升 25 秒），与 Windows `presets.json` 一致。
- `output/mac_pyautogui_poc/registry.py`：注册 `crealityscan.slide_rail_step`。
- `滑轨/mac操控滑轨方案/mac端Agent改动提示词.md`：可直接发给 Mac 端 Agent 的提示词（已含 preset 说明）。
- `滑轨/mac操控滑轨方案/mac_pyautogui_poc/`：可直接拷到 Mac `output/` 的完整改动包（含 `steps/presets.reference.json` 对照文件）。

> 已用本机临时 mock 服务（同协议）离线验证：step/right、step/left、get_position、move_absolute、emergency_stop、switch_position+preset（中物体/大物体默认上升 25 秒/lift 覆盖为 0）、未知 action/preset 抛错均符合预期；`py_compile` 通过。

## 7. 推荐落地步骤（半天量级）

1. 改 `motion_service.py`：`HOST='0.0.0.0'`（或配置化），重启服务（32 位 Python）。
2. Windows 防火墙放行 5000；Mac 上 `nc -vz` 验证连通。
3. 把 `motion_client.py` 放到 Mac 侧，先用一行脚本验证 `connect → connect_controller → move_relative → get_position → disconnect`。
4. 在 `mac_pyautogui_poc` 注册 `slide_rail_step`，暴露 `pulse`（±）参数，即得到与 Win 一致的"单步移动滑轨"。
5. （可选加固）服务端加全局命令锁 + token 鉴权；Mac 客户端加重试。

## 8. 附：setp（单步脉冲）与现有接口映射

Windows 控制台 `slide_rail_ui.py` 的"单步脉冲"区域：
- `pulse_spin` 输入脉冲数（默认 10000）
- "向左移动" → `move_relative(-abs(pulse))`
- "向右移动" → `move_relative(+abs(pulse))`
- 服务端 `cmd_horizontal_move` 会做软限位检查、按默认速度 80000 脉冲/秒移动、`wait_idle` 等待到位后返回新位置。

Mac 端复用同一接口即可，完全一致。若 Mac 也想看/记录位置，`get_position` / `position_logs` 逻辑同样可直接复用。

> 说明：Windows 的"单步脉冲（setp）"本身只有脉冲数输入，**不带 preset**；
> 位置预设（小物体/中物体/人脸/大物体）属于 Windows 平台的 `slide_rail.switch_position` step（`steps/slide_rail/switch_position/v1_0_0/presets.json`）。
> Mac 侧已把这两块都做了：`step` 用于手动单步，`switch_position`（配合 `preset`）用于按物体位置换位，行为与 Windows 平台一致。
