| 项目 | 内容 |
| --- | --- |

## 2. 项目定位

本工具用于对比发布版本和测试版本的 CrealityScan 对同一批原始工程执行相同后处理流程后的结果。

支持的后处理类型包括但不限于：

- 贴图
- 重贴图
- 人体补全
- 高斯渲染
- 后续新增的其他后处理 Step

工具负责自动准备隔离工程、顺序启动两个软件版本、导入工程、执行用户选择的后处理 Step、保存结果工程、截取对比图片，并生成并排报告和材料入口。

本期不自动判断哪个版本效果更好，最终判断由测试人员完成。

## 3. 建设目标

1. 保证两个软件版本使用来源一致、互不污染的工程副本。
2. 保证两个版本执行相同顺序、相同参数的后处理 Step。
3. 支持一个批次处理多个原始工程。
4. 自动保存每个版本的结果工程、最终截图、步骤结果和性能数据。
5. 某个工程或版本失败时尽量继续执行，最终仍生成可追溯的不完整报告。
6. 首先提供便于调试和批量运行的命令行内核，稳定后再建设独立 Qt 界面。
7. 保持工具与 Jens 主平台解耦，避免后处理对比任务影响现有自动化平台。

## 4. 明确不在本期范围内

- 自动判断两侧后处理效果优劣。
- 图片相似度评分、像素差异图和 AI 质量评分。
- 三个及以上软件版本的同批对比。
- 两个 CrealityScan 版本同时运行。
- Web 平台、账号权限和远程下发。
- 修改 CrealityScan 的后处理算法。
- 历史结果管理、检索和自动清理。
- 自动压缩或导出 ZIP。
- 主动收集全部 CrealityScan 日志。
- 截图自动裁剪。
- 工程复制进度条和暂停复制。
- 报告中的人工结论、缺陷编号和备注录入。
- 自动安装、升级或卸载 CrealityScan。

## 5. 已确认的产品规则

### 5.1 对比输出

- 生成发布版与测试版的并排报告。
- 报告提供截图、结果工程和执行明细入口。
- 不自动给出优劣结论。
- 即使部分步骤失败，也必须生成报告。
- 不完整报告需明确缺失哪一侧、哪个工程或哪个步骤。

### 5.2 工程隔离

CrealityScan 会直接修改导入的工程，因此禁止直接处理原始工程。

每个原始工程在后处理前必须创建两个独立工作副本：

```text
原始工程
├─ 发布版工作副本
└─ 测试版工作副本
```

工作副本完成处理后直接转为结果工程，不再额外复制大型工程。

### 5.3 多工程批处理

- 首版即支持添加多个原始工程。
- 用户提供一个原始工程集合，工具按配置顺序逐个处理。
- 一个工程失败后继续下一个工程。
- 只要任一工程或版本侧失败，最终批次状态为“部分失败”；配置、源工程损坏或工作副本创建失败等阻断性问题除外。

### 5.4 软件运行顺序

两个版本可以独立运行，但不能同时运行。固定执行顺序为：

1. 启动发布版。
2. 依次处理全部工程。
3. 正常关闭发布版并处理关闭确认弹窗。
4. 确认发布版进程退出。
5. 启动测试版。
6. 依次处理全部工程。
7. 正常关闭测试版并处理关闭确认弹窗。
8. 生成批次报告。

任何时候只允许存在一个由工具控制的 CrealityScan 进程。

### 5.5 后处理流程

- 工程路径指向工程目录。
- 工程导入使用独立 Step。
- 用户选择一个或多个后处理 Step，并配置顺序和参数。
- 同一工程中的多个 Step 允许连续执行，结果可以相互影响。
- 发布版和测试版必须使用相同的 Step ID、Step 版本、顺序和参数。
- 后处理完成同时支持 UI 标识和日志关键字判定。
- 默认单步超时为 10 分钟，可由 Step 或任务配置覆盖。
- 后处理完成后软件会自动保存工程，不额外判断保存状态。

### 5.6 截图规则

- 每个 Step 完成后是否截图可配置。
- 每个版本侧的最终截图必须生成。
- 截取整个屏幕，不自动裁剪。
- 工程会使用固定视角，工具不额外实现视角校正。
- 截图文件需关联批次、原始工程、软件版本和步骤。

### 5.7 版本与命名

- 软件版本标识由用户填写。
- 结果工程名称以“软件版本号 + 后处理名称”为核心规则。
- 为避免不同源工程或重复批次发生重名，工程名和批次时间戳由父目录承担隔离，不改变核心结果工程名称。
- 文件名中的 Windows 非法字符必须安全化处理。

### 5.8 性能记录

每个版本侧需要记录：

- 各 Step 处理耗时
- 工程总处理耗时
- CPU 使用情况
- 内存使用情况
- 结果工程大小

本期不要求主动收集完整软件日志，但执行完成判定所使用的日志关键字、命中时间和日志文件路径仍需记录。

## 6. 总体执行流程

```text
读取任务配置
  -> 校验发布版 EXE、测试版 EXE、工程集合、Step 和输出目录
  -> 采集 EXE 版本信息
  -> 检查磁盘空间
  -> 为每个工程创建发布版和测试版工作副本
  -> 启动发布版
     -> 导入工程 1 发布版副本
     -> 执行 Step 序列
     -> 可选逐步截图
     -> 必选最终截图
     -> 记录结果和性能
     -> 继续工程 2...N
  -> 关闭发布版并确认进程退出
  -> 启动测试版
     -> 导入工程 1 测试版副本
     -> 执行相同 Step 序列
     -> 可选逐步截图
     -> 必选最终截图
     -> 记录结果和性能
     -> 继续工程 2...N
  -> 关闭测试版并确认进程退出
  -> 生成 comparison.json
  -> 生成并排 report.html
  -> 输出批次状态
```

## 7. 失败处理规则

| 失败场景 | 处理规则 |
| --- | --- |
| 配置无效 | 阻止启动，指出具体配置项 |
| 原始工程损坏 | 当前工程两侧均不执行；记录失败并继续其他工程 |
| 工作副本创建失败 | 当前工程两侧均不执行；记录失败并继续其他工程 |
| 发布版启动失败 | 发布版侧失败；继续测试版侧和后续工程 |
| 发布版导入或后处理失败 | 保留现场材料；继续同一工程测试版和后续工程 |
| 测试版导入或后处理失败 | 保留发布版结果；继续后续工程 |
| 单个 Step 失败 | 按 Step 的 `abort`、`continue` 或 `retry` 策略 |
| 截图失败 | 记录错误；继续保留结果工程 |
| 正常关闭失败 | 最多重试 2 次；仍失败时记录并结束该版本进程 |
| 用户停止 | 停止当前 Step，关闭当前软件，不再执行后续版本或工程 |
| 报告生成局部失败 | 至少保留结构化 `comparison.json` 和已有材料 |

不稳定操作最多重试 2 次。元素未找到时必须截图，并记录具体异常和当前软件版本、工程、Step。

## 8. 弹窗处理策略

软件启动后可能出现升级提示、首次协议、登录、崩溃恢复等弹窗。采用可扩展的弹窗处理器：

1. 在启动完成和导入工程前执行弹窗扫描。
2. 按优先级匹配已登记模板。
3. 每种弹窗配置明确动作，例如关闭、稍后、接受或取消。
4. 未识别弹窗不得盲点，需截图并报告“未知阻塞弹窗”。
5. 关闭软件时单独处理确认弹窗。
6. 弹窗模板按 CrealityScan 版本兼容，不能假设两个版本界面完全相同。

首批模板在提供两个实际 EXE 和弹窗样例后补充。

## 9. 进程与窗口控制

- 使用用户提供的 EXE 路径启动软件。
- 记录进程 ID、EXE 完整路径、用户版本标签和启动时间。
- 自动化操作绑定本次启动的进程和窗口句柄。
- 不仅依赖相同的窗口标题识别版本。
- 启动新版本前确认旧版本进程已经退出。
- 关闭时优先发送正常关闭请求并处理确认弹窗。
- 超时后才允许结束进程，并记录是否发生强制结束。
- 已存在的非本工具 CrealityScan 进程默认视为冲突并阻止运行。

## 10. 命令行版本

### 10.1 开发优先级

首版优先开发命令行模式，用于验证：

- 配置模型
- 工程复制与隔离
- 软件生命周期
- Step 执行
- 失败恢复
- 截图
- 性能记录
- 报告生成

建议入口形式：

```powershell
python -m postprocess_compare validate task.json
python -m postprocess_compare run task.json
```

最终命令和模块名称以实现阶段为准。

### 10.2 命令行输出

运行时至少输出：

- 批次 ID
- 当前软件版本
- 当前工程序号和名称
- 当前 Step
- Step 开始、成功、失败和耗时
- 当前版本侧状态
- 工作副本和结果工程路径
- 报告路径
- 最终批次状态

退出码建议：

| 退出码 | 含义 |
| --- | --- |
| 0 | 全部成功 |
| 1 | 部分失败，报告已生成 |
| 2 | 配置或输入阻断，任务未开始 |
| 3 | 用户停止 |
| 4 | 工具内部错误 |

## 12. 建议代码结构

后处理对比工具使用独立运行内核，可以参考但不直接依赖 Jens 主平台界面代码：

```text
postprocess_compare/
├─ cli.py
├─ config.py
├─ models.py
├─ validator.py
├─ orchestrator.py
├─ process_manager.py
├─ project_workspace.py
├─ popup_handler.py
├─ step_runner.py
├─ metrics.py
├─ report.py
├─ qt_app.py
└─ tests/
```

模块职责：

| 模块 | 职责 |
| --- | --- |
| `config/models` | 任务配置和结果数据模型 |
| `validator` | EXE、工程、Step、输出目录和磁盘空间校验 |
| `orchestrator` | 版本侧、工程和 Step 的总流程编排 |
| `process_manager` | 软件启动、窗口绑定、正常关闭和强制结束 |
| `project_workspace` | 工作副本创建、命名、清单和结果工程管理 |
| `popup_handler` | 已知弹窗识别与未知弹窗留证 |
| `step_runner` | 动态加载并执行后处理 Step |
| `metrics` | CPU、内存、耗时和工程大小统计 |
| `report` | `comparison.json` 和 `report.html` |
| `qt_app` | 后续独立 Qt 页面 |

独立内核可以复用或迁移 Jens 中稳定的基础能力，但不能依赖 Jens 主窗口对象或主平台运行状态。

## 15. 报告要求

报告至少包含：

- 批次名称、ID、起止时间和总状态
- 两个软件的用户版本标签、EXE 路径和文件版本
- 原始工程列表
- 工作副本创建状态
- 两侧实际 Step、版本、参数、状态、耗时和重试次数
- 每个工程两侧最终截图并排展示
- 可选的逐 Step 截图
- CPU、内存、工程总耗时和结果工程大小
- 失败截图、异常和完成标识
- 结果工程和材料目录入口
- 部分失败时的报告完整性说明

报告不提供自动评分、人工结论输入或历史管理功能。

## 16. 数据安全要求

- 原始工程只读，不允许直接导入处理。
- 任何删除操作前必须确认目标位于本批次工作目录。
- 默认不覆盖历史批次。
- 工作副本创建失败时不得使用半成品继续测试。
- 记录复制失败的具体文件和异常类型。
- 文件复制最多重试 2 次。
- 支持中文、空格和长路径。
- 结果目录不能位于原始工程内部。
- 创建工作副本前检查可用磁盘空间。
- 任务配置和报告中保存完整路径，但不记录账号、密码等凭据。

## 17. 验收标准

### AC-01 配置校验

两个 EXE、版本标签、至少一个工程、至少一个 Step 和输出目录有效时允许运行；无效时指出具体字段。

### AC-02 原始工程保护

执行前为两个版本创建独立工作副本，任务结束后原始工程内容未被修改。

### AC-03 多工程执行

同一批次可处理多个工程，一个工程失败后仍继续后续工程。

### AC-04 版本串行

发布版全部处理完成并退出后才能启动测试版，运行期间不存在两个受控版本同时运行。

### AC-05 操作一致

两个版本对同一工程使用完全一致的主 Step ID、版本、顺序和参数。

### AC-06 完成判定

每个后处理 Step 通过 UI 或日志完成标识判定成功，不能仅靠固定等待；默认超时 10 分钟且可配置。

### AC-07 结果工程

每个成功版本侧的工作副本直接成为结果工程，目录名称包含用户版本标签和后处理名称。

### AC-08 截图

每个版本侧必须有全屏最终截图；配置开启时每个 Step 结束后也有截图。

### AC-09 部分失败

发布版、测试版或单个工程失败时继续执行允许的后续项，并生成标记为“部分失败”的报告。

### AC-10 进程关闭

工具能够处理正常关闭确认弹窗；关闭失败时重试并记录最终处理方式。

### AC-11 性能记录

报告包含步骤耗时、工程总耗时、CPU、内存和结果工程大小。

### AC-12 命令行运行

首版可通过命令行完成配置校验和完整批次运行，并用退出码区分成功、部分失败、阻断和用户停止。

- 命令行内核集成

## 19. 实施前需要提供的输入

以下内容属于开发输入，不再属于产品需求疑问：

1. 一对可运行的发布版和测试版 EXE。
2. 用户填写的两个版本标签示例。
3. 至少一个可复制的测试工程。
4. 工程有效性最低识别规则。
5. 第一批后处理 Step 的名称、操作、参数和完成标识。
6. 导入工程 Step 的现有实现或路径。
7. 每类后处理的最终效果页面截图示例。
8. 两个版本中可能出现的启动、升级、协议和关闭弹窗截图。
9. UI 和日志完成标识的实际样例。
10. 典型工程大小及各后处理可接受的超时范围。

以上输入齐备后，可以直接进入命令行版本的技术设计与实现。
