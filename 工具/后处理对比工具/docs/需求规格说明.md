| 编写日期 | 2026-08-06 |

## 2. 背景与目标

CrealityScan 的发布版本和当前测试版本可能对同一原始工程产生不同的后处理效果，例如：

- 贴图
- 重贴图
- 人体补全
- 高斯渲染
- 后续新增的其他后处理操作

本工具用于让用户选定两个 CrealityScan 可执行程序、一个或多个原始工程以及需要执行的后处理 Step，然后自动按相同条件依次运行两个软件版本，保存处理后的完整工程、截图、日志和执行记录，为版本间效果评审提供可追溯的对比材料。

### 2.1 核心目标

1. 保证发布版和测试版使用来源一致、互不污染的工程输入。
2. 保证两个版本执行相同顺序、相同参数的后处理操作。
3. 自动保存每个版本的后处理工程副本和结果截图。
4. 清晰显示当前版本、当前工程、当前 Step 和整体进度。
5. 在失败时保留截图、日志和失败位置，支持定位版本回归。
6. 复用现有 Jens Runner 和 Step 机制，避免重新实现自动化执行内核。

### 2.2 成功标准

用户完成一次配置后，无需手工切换软件版本或重复执行相同步骤，即可获得两个版本彼此隔离、命名清晰、能够对应同一源工程和同一操作序列的结果材料。

## 3. 术语

| 术语 | 定义 |
| --- | --- |
| 发布版/旧版本 | 用作对照基准的 CrealityScan 版本，由用户选择 EXE |
| 测试版/新版本 | 当前待验证的 CrealityScan 版本，由用户选择 EXE |
| 原始工程 | 用户提供、用于两个版本对比的 CrealityScan 工程 |
| 工作副本 | 从原始工程复制出的独立运行输入，供某一个软件版本处理 |
| 结果工程 | 完成所选后处理操作后保存的完整工程目录 |
| 后处理 Step | 封装单个后处理动作的 Jens Step，具体实现由需求方后续提供 |
| 对比任务 | 两个软件版本、工程、Step 序列和输出规则组成的一次配置 |
| 对比批次 | 用户点击运行后产生的一次完整执行及其所有结果 |
| 版本侧 | 发布版侧或测试版侧的一组输入、执行状态和输出 |

## 4. 范围

### 4.1 本期范围

- 选择发布版和测试版的 EXE 路径。
- 选择原始工程路径。
- 选择并排序后处理 Step。
- 启动、等待和关闭指定版本 CrealityScan。
- 为两个版本准备彼此独立的工程输入。
- 导入工程并执行所选 Step。
- 在规定时机截图。
- 保存处理后的完整工程。
- 记录进度、日志、步骤结果、版本信息和输出路径。
- 先执行发布版，再执行测试版。
- 支持停止当前对比任务。
- 生成本次对比批次的结果清单或报告。

### 4.2 暂不纳入，除非待确认问题另有结论

- 自动判断哪个版本的后处理视觉效果更好。
- 三个及以上软件版本同时对比。
- 多台电脑分布式执行。
- Web 登录、远程任务下发和多人权限。
- 修改或实现具体后处理算法。
- 自动安装、升级或卸载 CrealityScan。
- 直接修改现有 Jens 主平台业务流程。
- 在本文档阶段实现具体后处理 Step。

## 5. 用户与使用场景

### 5.1 目标用户

- CrealityScan 测试人员
- 后处理算法验证人员
- 版本发布验收人员

### 5.2 典型场景

测试人员需要验证当前测试版本相对于已发布版本是否出现贴图或人体补全效果回退。测试人员选择两个 EXE、同一原始工程和相同后处理 Step，启动任务后离开操作现场。工具依次完成两个版本的处理，最终提供两个结果工程、截图和执行报告，供人工或后续算法进行对比。

## 6. 总体业务流程

```text
创建对比任务
  -> 选择发布版 EXE
  -> 选择测试版 EXE
  -> 选择原始工程
  -> 选择并排序后处理 Step
  -> 选择结果输出目录
  -> 校验配置
  -> 为两个版本创建独立工作副本
  -> 启动发布版
  -> 导入发布版工作副本
  -> 执行相同 Step 序列
  -> 截图并保存发布版结果
  -> 关闭发布版
  -> 启动测试版
  -> 导入测试版工作副本
  -> 执行相同 Step 序列
  -> 截图并保存测试版结果
  -> 关闭测试版
  -> 生成结果清单/报告
```

固定执行顺序为：

1. 发布版/旧版本。
2. 测试版/新版本。

除非用户明确停止，否则旧版本某一工程失败后是否继续测试版本或后续工程，按照第 12 节待确认策略执行。

## 7. 输入需求

### 7.1 软件版本

用户必须提供：

- 发布版 CrealityScan EXE 路径。
- 测试版 CrealityScan EXE 路径。

系统应校验：

- 路径非空。
- 文件存在且扩展名为 `.exe`。
- 两个路径不能完全相同；若相同，应提示用户确认或禁止运行，具体策略待确认。
- 运行前能够启动进程。
- 应记录 EXE 文件名、完整路径、文件版本、产品版本和文件哈希；无法读取时记录为空并给出提示。

### 7.2 原始工程

用户必须提供至少一个 CrealityScan 工程路径。

建议支持：

- 选择单个工程目录。
- 一次添加多个工程目录形成批处理列表。
- 从列表移除工程。
- 调整工程执行顺序。
- 为每个工程显示名称、路径和校验状态。

系统应校验：

- 路径存在且为目录。
- 当前用户具有读取权限。
- 工程结构符合 CrealityScan 可导入工程的最低规则。具体识别文件待确认。
- 输出目录不能位于原始工程内部。
- 多个列表项不能指向同一规范化路径。

### 7.3 后处理 Step

用户应从可用 Step 列表中选择一个或多个后处理操作，并能调整执行顺序。

每个 Step 至少展示：

- Step ID
- 名称
- 版本
- 描述
- 参数
- 当前顺序

两个软件版本默认必须使用完全相同的 Step ID、版本、顺序和参数。若后续需要版本专属动作，应新增明确的“版本前置/后置 Step”能力，不能隐式改变主对比序列。

具体后处理 Step 由需求方后续提供，不属于本文档的实现输入。

### 7.4 输出目录

用户必须选择对比结果根目录。系统应校验：

- 路径可创建或已存在。
- 当前用户具有写入权限。
- 剩余空间满足工作副本、结果工程、截图和日志需求。
- 不能覆盖原始工程。
- 同名批次默认创建新目录，不静默覆盖历史结果。

## 8. 工程隔离与复制要求

### 8.1 推荐基线

在任何版本打开工程前，系统应从原始工程创建两个独立工作副本：

```text
原始工程（只读基准）
├─ 发布版工作副本
└─ 测试版工作副本
```

发布版和测试版只能操作各自工作副本，不应直接打开同一个原始工程，也不应让测试版读取发布版处理后的工程。

原因：如果 CrealityScan 在打开、导入或后处理期间修改工程文件，按“旧版先执行”直接复用原工程会使新版输入发生变化，导致对比无效。

该基线需要需求方确认，但在未确认 CrealityScan 是否原地写入前，不建议采用“处理后才复制工程”的原始流程。

### 8.2 复制规则

- 复制前统计工程大小并检查磁盘空间。
- 复制失败时最多重试 2 次。
- 捕获并记录具体失败文件和异常类型。
- 工作副本创建完成后记录文件数量、总大小和创建时间。
- 不允许使用已存在且含内容的目录作为新工作副本，除非用户明确选择覆盖；建议本期禁止覆盖。
- 处理完成后，版本工作副本可直接作为结果工程保留，避免再次复制超大工程。该策略待确认。
- 若必须“处理完成后再复制到结果目录”，应先关闭或释放 CrealityScan 对工程文件的占用，再执行复制。

## 9. 软件进程生命周期

每个版本侧应执行：

1. 确认另一个 CrealityScan 进程未运行。
2. 使用用户选择的 EXE 启动软件。
3. 等待目标窗口和软件就绪。
4. 记录进程 ID、启动时间和版本信息。
5. 执行导入工程和后处理 Step。
6. 完成截图和工程保存。
7. 请求正常关闭软件。
8. 超过关闭超时后提示并按确认策略强制结束进程。
9. 确认进程退出后才能启动另一个版本。

系统不得仅根据窗口标题假设启动的是正确版本，应将 Runner 绑定到本次启动的进程 ID，或至少同时校验 EXE 路径、进程 ID 和窗口句柄。

启动前若检测到已有 CrealityScan 进程，处理方式待确认。

## 10. 自动化执行要求

### 10.1 执行内核

- 复用现有 Jens Step 动态加载和 Runner 执行机制。
- Step 仍按 `step_id + version` 映射到 `run(ctx, params)`。
- 每个版本侧应有独立的运行上下文、日志段、步骤结果和产物目录。
- 失败策略支持 `abort`、`continue`、`retry`。
- 不稳定操作最多重试 2 次，具体 Step 可配置更低次数。
- 元素或模板未找到时必须截图。
- 捕获控制台输出和具体异常，不使用只有“执行失败”的模糊错误。
- 应支持用户请求紧急停止；停止后不得继续启动下一版本。

### 10.2 导入工程

导入工程应封装为独立 Step 或受控流程，并满足：

- 使用当前版本对应的工作副本。
- 等待工程加载完成标识，不以“点击导入”作为完成。
- 加载超时应保存截图和日志。
- 导入完成后记录工程路径和加载耗时。
- 两个版本使用同一套加载完成判定；若日志格式不同，可配置版本兼容关键字，但应输出实际命中的标识。

### 10.3 后处理执行

- 按用户选择顺序执行 Step。
- 两个版本使用相同参数。
- 每步显示状态：等待、运行、成功、失败、跳过、停止。
- 每步记录开始时间、结束时间、耗时、尝试次数和错误。
- 长耗时后处理必须有明确的完成判定和超时，不能只使用固定等待。
- 若操作会生成多个可视结果，应明确当前截图和工程保存对应哪个结果。

## 11. 截图与对比材料

### 11.1 基本要求

- 每个版本至少生成一张最终效果截图。
- 截图必须标识版本侧、工程名、Step 或阶段、时间。
- 截图文件名不能依赖中文窗口标题，需经过安全化处理。
- 截图失败应记录错误，但是否阻断工程保存待确认。
- 两个版本应尽量保持相同窗口尺寸、视图模式、相机角度、缩放和渲染设置。

### 11.2 推荐截图阶段

以下方案待确认：

- 每个后处理 Step 完成后截图一次。
- 全部 Step 完成后再截图一次最终效果。
- 若需多角度对比，由额外的“视角设置 Step”确定固定角度后截图。

仅保存“当前屏幕截图”不足以保证可比性。若用户在两个版本间得到不同视角，截图无法直接进行视觉判断，因此需要固定视角规则或由 Step 明确设置视图。

### 11.3 自动对比

当前原始需求只明确“保存用于对比的截图和工程”，没有明确是否需要：

- 并排展示。
- 图片叠加。
- 像素差异图。
- 相似度或质量评分。
- 人工填写结论。

在需求方确认前，本期按“收集和组织对比材料，不自动判断优劣”处理。

## 12. 失败与继续策略

需要支持以下失败位置：

- EXE 校验失败。
- 软件启动或关闭失败。
- 工程复制失败。
- 工程导入失败。
- Step 执行失败或超时。
- 截图失败。
- 工程保存/复制失败。
- 磁盘空间不足。
- 用户停止。

推荐默认策略：

| 失败场景 | 推荐行为 |
| --- | --- |
| 配置校验、工作副本创建失败 | 不启动任何版本，任务失败 |
| 发布版启动或导入失败 | 保存现场；是否继续测试版待确认 |
| 某个后处理 Step 失败 | 按该 Step 的 on_fail 策略 |
| 截图失败 | 记录失败，继续尝试保存工程 |
| 结果工程保存失败 | 当前版本侧失败 |
| 测试版失败 | 保存已完成的发布版结果并结束 |
| 用户停止 | 停止当前 Step，关闭当前软件，不再执行后续版本或工程 |

批量工程模式下，还需要确认“一个工程失败后是否继续下一个工程”。

## 13. 进度与界面需求

建议创建独立的桌面工具页面，或在现有 Qt 平台增加独立入口。最终形态待确认。

界面至少包含：

### 13.1 配置区

- 发布版 EXE 路径输入框和选择按钮。
- 测试版 EXE 路径输入框和选择按钮。
- 原始工程列表及添加、移除、排序操作。
- 结果输出目录。
- 后处理 Step 列表、参数和顺序。
- 超时和失败策略的高级设置。

### 13.2 运行控制区

- 开始运行。
- 紧急停止。
- 当前批次状态。
- 当前软件版本。
- 当前工程。
- 当前 Step。
- 总体进度和版本侧进度。
- 已用时间。

### 13.3 日志与结果区

- 实时日志窗口。
- 按版本侧分组的步骤结果。
- 失败截图入口。
- 发布版/测试版结果工程入口。
- 截图入口。
- 批次报告入口。

运行中应锁定会改变输入基线的配置项，防止界面显示配置与实际执行配置不一致。

## 14. 结果目录建议

建议结构：

```text
<输出根目录>/
└─ <批次名>_<时间戳>/
   ├─ comparison.json
   ├─ report.html
   ├─ logs/
   └─ projects/
      └─ <工程安全名称>/
         ├─ source_manifest.json
         ├─ release/
         │  ├─ project/
         │  ├─ screenshots/
         │  ├─ result.json
         │  └─ logs/
         └─ test/
            ├─ project/
            ├─ screenshots/
            ├─ result.json
            └─ logs/
```

最终命名规则待确认。无论采用何种目录结构，都必须能从任一截图或结果工程反查：

- 对比批次。
- 原始工程。
- 软件版本侧。
- EXE 版本信息。
- Step 序列和参数。
- 执行时间。
- 成功/失败状态。

## 15. 结果清单与报告

每个批次至少生成一份结构化 `comparison.json`，建议同时生成 `report.html`。

报告至少包含：

- 批次 ID、名称、起止时间和总状态。
- 发布版、测试版 EXE 路径、版本号和文件哈希。
- 原始工程路径及源工程清单。
- 工作副本/结果工程路径。
- 实际 Step ID、版本、顺序和参数。
- 两个版本各步骤状态、耗时、重试和错误。
- 两侧最终截图或缩略图。
- 日志和工程目录入口。
- 用户停止信息。
- 待人工填写的对比结论，是否需要待确认。

若任一版本失败，报告仍应生成，并明确“无法完成效果对比”的原因。

## 17. 非功能需求

### 17.1 可重复性

- 两个版本使用独立且来源一致的工程副本。
- 固定 Step、参数、视图和执行顺序。
- 保存完整配置快照，后续可复跑。

### 17.2 可追溯性

- 每个结果能定位到软件版本、源工程、Step 和时间。
- 所有异常包含具体阶段和原因。
- 失败必须保留截图和相关日志。

### 17.3 安全性

- 默认不修改或删除原始工程。
- 默认不覆盖历史结果。
- 删除临时工作副本前必须确认其不是唯一结果。
- 强制结束进程前先尝试正常关闭。
- 不在日志中打印敏感路径以外的凭证数据。

### 17.4 稳定性

- 文件复制和日志读取失败最多重试 2 次。
- 每个长操作都有可配置超时。
- 进程、窗口和 Step 状态必须一致。
- 单个错误不能导致报告完全缺失。

### 17.5 兼容性

- 支持包含中文、空格和较长名称的 Windows 路径。
- 支持两个版本安装在不同目录。
- 需要验证两个版本是否共享用户配置、缓存和日志目录；若共享，应提供隔离或清理策略。

### 17.6 性能

- 大型工程复制时显示进度或至少显示已用时间和当前状态。
- 不在 UI 主线程执行工程复制和自动化。
- 运行前估算至少两份工程副本及产物需要的空间。

## 18. 验收标准

### AC-01 配置校验

给定有效的两个 EXE、工程和输出目录，系统允许启动；缺失或不可访问时阻止启动并指出具体字段。

### AC-02 输入隔离

一次任务运行后，发布版和测试版使用两个独立工程目录，原始工程未被修改。

### AC-03 顺序执行

系统先完成发布版侧的启动、导入、Step、截图和保存，再启动测试版；任意时刻默认只存在一个受控 CrealityScan 进程。

### AC-04 操作一致

报告中两个版本的主后处理 Step ID、版本、顺序和参数完全一致。

### AC-05 结果保存

每个成功版本侧都有完整结果工程、最终截图、步骤结果和日志入口，命名不会覆盖历史批次。

### AC-06 失败现场

任一 Step 找不到元素或超时时，系统保留失败截图、具体异常和当前版本/工程/Step 信息。

### AC-07 停止

用户停止后，系统不再启动下一版本或下一工程，并尝试安全关闭当前进程。

### AC-08 报告完整

即使某一版本失败，批次仍生成结构化结果和报告，并明确失败导致的对比完整性。

### AC-09 路径兼容

包含中文和空格的 EXE、工程及输出路径可以正常校验、复制和记录。

### AC-10 可复跑

使用报告中的配置快照可以重新创建等价任务，且不会覆盖第一次结果。

## 19. 待确认问题

以下问题会影响数据安全、执行流程或验收标准，建议开发前逐项确认。

### P0：必须确认

1. “对比效果”是只保存两侧工程和截图供人工查看，还是工具必须提供并排页面、图片差异或自动评分？
   - 推荐默认：本期生成并排报告和材料入口，不自动判断优劣。

2. CrealityScan 在导入、打开或后处理时是否会直接修改原工程？
   - 推荐默认：无论是否确认原地修改，都先为两个版本各创建一个工作副本，原工程只读。

3. 输入是一次只处理一个工程，还是必须支持多工程批量运行？
   - 推荐默认：数据结构支持多工程，首版界面也允许添加多个工程。

4. 工程路径指向目录还是某个工程文件？判断“有效 CrealityScan 工程”的标志文件或目录是什么？

5. 处理完成后的工程是：
   - 直接保留版本工作副本；
   - 还是关闭软件后再复制到单独结果目录？
   - 推荐默认：工作副本直接转为结果工程，减少大型工程的重复复制。

6. 截图需要在每个 Step 后、全部 Step 后，还是由 Step 自己声明截图时机？
   - 推荐默认：每步后截图可配置，最终截图必选。

7. 如何保证两个版本截图视角一致？是否已有“设置固定视角/缩放/渲染模式”的 Step？

8. 发布版执行失败时，是否仍继续执行同一工程的测试版？
   - 推荐默认：继续测试版并生成不完整对比报告，除非失败原因是输入工程损坏或工作副本失败。

9. 批量模式下，一个工程失败后是否继续下一个工程？
   - 推荐默认：继续下一个工程，最终批次状态为部分失败。

10. 两个 CrealityScan 版本是否能在同一台电脑独立运行？是否共享配置、缓存、插件、日志和用户数据目录？

### P1：影响功能设计

11. 工具做成独立 Qt 应用，还是集成到现有 Jens 主平台的一个页面？
    - 推荐默认：先做独立入口但复用内部模块，降低对现有任务平台的影响。

12. EXE 启动是否需要命令行参数、工作目录、管理员权限或特定环境变量？

13. 启动后是否存在升级提示、首次使用协议、登录、崩溃恢复或其他需要处理的弹窗？

14. 两个版本的窗口标题是否完全相同？是否能通过进程 ID 和窗口句柄稳定绑定？

15. 软件正常关闭时，未保存状态是否会弹窗？应该点击保存、放弃还是取消？

16. 用户选择的主后处理 Step 是否必须在两个版本完全相同？是否允许配置“仅发布版”或“仅测试版”的兼容步骤？

17. 贴图、重贴图、人体补全、高斯渲染的完成标识分别来自 UI、日志还是输出文件？默认超时是多少？

18. 一次工程是否允许连续执行多个互相影响的后处理 Step，还是每个 Step 都应从原始工程的独立副本开始？
    - 这决定比较的是“组合流程”还是“单项算法”。

19. 结果工程的命名规则是什么？是否需要包含源工程名、版本号、Step 名、时间戳？

20. 用户是否需要保存对比任务模板，下次直接选择并复跑？

21. 是否需要在报告中让用户填写人工结论、缺陷编号、备注和通过/不通过？

22. 是否需要自动收集 CrealityScan 自身日志？两个版本的日志目录如何定位和区分？

### P2：可后续确认

23. 是否需要工程复制进度条、暂停复制或取消复制？

24. 是否需要对结果工程进行压缩，便于传输或归档？

25. 历史结果是否需要在工具中搜索、筛选和删除？保留周期是多少？

26. 是否需要导出一份可发给开发人员的 ZIP，包含报告、截图和精简日志？

27. 是否需要对截图自动裁剪到模型区域，隐藏工具栏等无关 UI？

28. 是否需要记录 CPU、内存、处理耗时和结果工程大小，用于性能回归对比？

29. 是否需要支持不打开 GUI 的命令行批量模式？

30. 软件版本的唯一标识以什么为准：文件版本、产品版本、Git 提交号、安装目录名还是用户填写标签？
